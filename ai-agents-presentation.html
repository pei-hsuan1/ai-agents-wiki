概念 01 · 核心定義與類比

AI Agent 的黃金公式與「餐廳主廚」類比

如果把傳統聊天機器人比喻為「只會回答食譜的顧問」，AI Agent 就是「能自己進廚房把菜做出來的主廚」。

AI Agent = LLM (核心大腦) + Planning (規劃) + Memory (記憶) + Tool Use (工具使用)

🧠 LLM 大腦 + 📋 Planning 規劃

接到「準備三人晚餐」的目標後，大腦會自動拆解子任務：先看食材 → 決定菜單 → 安排烹飪先後順序。

🗂️ Memory 記憶 + 🔧 Tool Use 工具

記憶負責記住客人的飲食禁忌（短期）與過往食譜（長期）；工具則是爐具、烤箱與外送採購 App。

核心架構公式源自 Lilian Weng (2023) 知識來源：wiki/01-agent-overview.md [Source 1]
概念 01 · 觀念釐清

Chatbot vs. Workflow vs. AI Agent 差在哪？

並不是所有 AI 應用都需要做成 Agent！了解三者邊界才能選對最適合的工具。

比較維度 傳統 Chatbot（聊天機器人） Workflow（固定工作流） AI Agent（自主代理）
決策控制權 完全由人類一問一答引導 由工程師預先寫死程式碼路徑 由 LLM 動態決定下一步路徑
外部行動力 僅能產生文字回覆 按固定順序呼叫指定 API 自主挑選工具並根據結果調整
最佳適用場景 腦力激盪、單次問答翻譯 步驟固定、規則明確的標準流程 步驟無法預先窮舉的複雜開放任務
設計原則：步驟固定用 Workflow，需要動態應變才用 Agent 知識來源：wiki/01-agent-overview.md [Source 3]
概念 02 · 任務規劃 (Planning)

大腦如何面對複雜任務？先拆解再執行

人類不會一口氣寫完十萬字論文，AI Agent 也需要透過「子目標拆解（Subgoal Decomposition）」降低出錯率。

🎯 範例指令：「幫我規劃下週去東京的 3 天自由行並寄出行程表」

若直接要求模型一次輸出，極易遺漏細節或編造營業時間。透過 Chain-of-Thought（思維鏈） 拆解後：

步驟 1：條件確認

查詢下週東京天氣預報，確認室內與戶外景點的分配比例。

步驟 2：路線與檢索

依區域（新宿、淺草）檢索高評價餐廳與交通時間，排定每日時間軸。

步驟 3：格式化與交付

檢查是否有時間衝突，將最終行程表整理成文件並呼叫郵件工具寄出。

先規劃大綱再逐步落實，是提升 Agent 成功率的關鍵 知識來源：wiki/02-planning-and-react.md [Source 1, Source 4]
概念 02 · 互動模擬器

ReAct 迴圈：思考 (Thought) × 行動 (Action) × 觀察 (Observation)

點擊下方按鈕，親自體驗 Agent 如何回答：「今天台北適合穿短袖嗎？」

[Thought 1 思考] 使用者問今天台北適合穿短袖嗎。我無法憑空猜測即時氣溫，必須先查詢台北今天的氣象預報。
交錯執行推理與外部觀察，可大幅減少 AI 憑空捏造（幻覺） 知識來源：wiki/02-planning-and-react.md [Source 2]
概念 03 · 記憶系統 (Memory)

短期記憶 vs. 長期記憶：工作桌面與圖書館

沒有記憶的 AI 每次對話都像「金魚只有七秒記憶」；完整的記憶架構讓 Agent 能累積經驗。

📝 短期記憶（Short-Term Memory）

  • 技術載體：模型的上下文視窗（Context Window）。
  • 生活類比：書桌上的「便利貼與草稿紙」。
  • 存放內容：當下對話紀錄、剛執行的 ReAct 軌跡、以及上一輪失敗的反思筆記。
  • 限制：桌面空間有限，塞滿會遺忘最早的內容。

🏛️ 長期記憶（Long-Term Memory）

  • 技術載體：外部向量資料庫（Vector Store）與知識庫（如本作業的 LLM Wiki）。
  • 生活類比：身後的「大型圖書館書架」。
  • 運作方式：平時不佔用桌面，需要時透過語意檢索（Retrieval）把最相關的資料抽到桌面上使用。
本作業建立的 LLM Wiki，正是扮演 Agent 的「結構化長期記憶庫」 知識來源：wiki/03-memory-system.md [Source 1, Source 5]
概念 04 · 工具使用 (Tool Use)

讓 AI 長出手腳：Function Calling 運作三步驟

LLM 本身只會輸出文字，它並不會「親自」按滑鼠，而是透過與程式執行層（Runtime）協作來操作工具。

1️⃣ LLM 輸出結構化指令

模型判斷需要算數學或查資料時，輸出標準 JSON 呼叫請求，例如：
calc_tax(income=850000)

2️⃣ 系統執行層 (Runtime) 接手

外部程式碼接收 JSON 指令，實際執行 Python 計算或呼叫官方 API，取得精準結果：{"tax": 42500}

3️⃣ 回傳數據組織回答

系統把真實數據塞回給 LLM 作為 Observation，由 LLM 翻譯成自然流暢的人類語言回覆。

💡 工具設計關鍵（Agent-Computer Interface, ACI）

Anthropic 研究指出：提供給 Agent 的工具必須具備清楚的用途說明、防呆參數格式與明確錯誤提示，才能避免模型呼叫失敗。

Tool Use 讓語言模型突破預訓練知識截止日期與數學計算短板 知識來源：wiki/04-tool-use.md [Source 1, Source 3, Source 4]
概念 05 · 自我反思與設計模式

Reflection（自我反思）：做錯了怎麼自己改？

Andrew Ng 指出：讓 AI 透過「反覆檢查迭代（Iterative Workflow）」工作，表現往往超越單次生成的更大模型。

🪞 Reflexion 自我修正三元迴圈

  • Actor（行動者）：先產出初版解答或程式碼。
  • Evaluator（評估器）：對照規則檢查是否出錯或超譯。
  • Self-Reflection（反思模組）：若未通過，把「失敗原因」寫成文字規則存入短期記憶，引導下一輪避開相同錯誤！

🧩 四大 Agentic 設計模式總覽

  • Reflection（自我反思）：自己審查草稿並改寫。
  • Tool Use（工具使用）：呼叫搜尋、程式與 API。
  • Planning（任務規劃）：先拆解多步驟計畫。
  • Multi-Agent（多代理協作）：分飾「撰稿者」與「審查員」分工把關。
這套「生成 → 檢查 → 反思修正」迴圈，也是本作業 Workflow 的核心設計 知識來源：wiki/05-reflection-loop.md [Source 4, Source 5]
